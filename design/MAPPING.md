## Implementation notes

- `/(app)/(tabs)/today` macro tiles use the supplied photography, named for the macro each depicts: `assets/images/food-protein.png` (grilled chicken), `assets/images/food-carbs.png` (rice bowl), and `assets/images/food-fat.png` (avocado and nuts). Each sits in a circular tinted well at the tile's lower-left, per `main-dashbaord.png`, sized with fixed classes, and marked `accessible={false}` because the adjacent value and label already carry the meaning.
- `/(app)/scan/camera` (before permission) renders `assets/images/welcome-food-scan-hero.png` as the hero, with the tip icons matching `camera-open-before.png`: viewfinder, sun, eye. Its CTA carries no icon; the permanently-denied variant adds a settings icon as a documented adaptation.
- **Accepted deviation — bottom navigation.** The tab bar uses `expo-router/unstable-native-tabs`, giving a real `UITabBar` on iOS and a Material 3 navigation bar on Android, with the platform's own selection animation, haptics, blur, safe-area handling and Dynamic Type. `NativeTabs` accepts only `Icon`, `Label` and `Badge` as children, so **the elevated centre Scan button in `main-dashbaord.png` and `camera-open-before.png` is not implemented**; Scan is a flat tab. This was an explicit product decision, not an oversight.
- Selected and unselected tab artwork is supplied to the platform through the `default`/`selected` icon forms (`sf` on iOS, `md` on Android) rather than switched in JavaScript. Progress, Scan and Foods have no filled counterpart in either icon set, so tint alone marks their selected state.
- Scan blocks native selection via the trigger's `disabled` prop, which maps to `preventNativeSelection` — it refuses the selection at the tab-bar controller rather than dimming the item — and pushes `/(app)/scan/camera` from the still-emitted `tabPress`. Native `tabPress` is not cancelable, so this replaces the previous `preventDefault` interception.
- Native tabs render no header. The Today brand lockup with its streak badge, and the Profile title with its notifications action, are now drawn inside those screens, which also take the top safe-area edge.
- Images that need `className` must import `Image` from `@/tw`, not from `expo-image`. Only the wrapper converts `className` into a style — imported bare, sizing classes are silently discarded and the image collapses to zero height.
- The Apple authentication button uses the `apple.logo` SF Symbol, tinted white on the black button. It was briefly `assets/images/apple-sign-in-logo.png`, added because Material Symbols has no Apple counterpart — but that file was a filled rounded square rather than the Apple mark, so it drew a white tile on both platforms; it has been removed. Android shows the label without a glyph until the official artwork from Apple's Sign in with Apple design resources is bundled.
- Unused supplied assets, kept but not currently mapped to any route: `BodyCal-White-Logo.png`, `daily-goal-runner.png`, `logo-glow.png`, `muscular-body-man.png`, `muscular-body-man-hero.png`. `assets/images/tabIcons/` and the `expo-*`/`react-logo*`/`tutorial-web` files are unused Expo template leftovers.
- `/(public)/welcome` uses `assets/images/welcome-food-scan-hero.png`, derived from the user-supplied person-photographing-food reference with its phone frame and instruction UI removed.
- The language badge in `welcome.jpg` shows only its closed state. In the app it opens a native form sheet containing all eight launch languages, with radio semantics and a persisted selection.
- The sign-in entry follows the authentication bottom-sheet pattern in `DESIGN-SYSTEM.md`; choosing email opens the mapped email/password screen within the same native sheet stack.
- Responsive height, Dynamic Type, screen-reader semantics, and 44-point minimum targets take precedence over fixed mockup coordinates.
- Sign-in and sign-up remain mapped but are not visually accepted by this welcome-screen change.
- `design-system.png` and `DESIGN-SYSTEM.md` jointly define the shared BodyCal foundations. Where fixed mockup geometry conflicts with Dynamic Type, safe areas, localization, or smaller Android displays, the responsive native behavior takes precedence.
- The calculation-basis options carry distinct glyphs. Both were `person.fill` on iOS, so the two cards rendered the identical mark and the icon carried no information; SF Symbols has no Mars/Venus pair, so iOS uses `figure.stand` and `figure.stand.dress` (SF Symbols 4, iOS 16) while Android keeps Material's `male`/`female`, which were already distinct.
- Onboarding choice cards mark selection by inverting the icon chip to the ink fill with a white glyph, in addition to the border and radio dot. The border now holds a constant 1.5px and changes only colour — it previously grew from 1px on selection, shifting the row by half a point on every change of mind.
- `ChoiceScreen` takes an opt-in `layout="row"`, which lays the options out as equal-width flex tiles instead of full-width rows. Calculation basis uses it: two one-word labels, so the tiles sit side by side with the glyph above the label and the filled chip carrying the whole selected state. It stays opt-in rather than a width rule — activity, goal and pace each pair a label with a description that needs the full width to wrap at large text sizes.
- The basis labels are the plain words (`Male`, `Female`, and their eight-language equivalents), not `Male-based formula`. The shortened strings were taken verbatim from `personalDetails.male`/`female`, which already named the same choice on the settings screen, so no translation was authored for this change. The screen carries no explanatory paragraph under the tiles; `personalDetails.basisHint` still explains the choice on the settings screen, where it can be changed later.
- The screen-2 reference includes a third undisclosed-sex choice. It is intentionally not mapped to an invented Mifflin–St Jeor formula constant; the implemented choices state the required calculation basis explicitly pending a product decision.
- The Results CTA retains the existing account-creation boundary. Successful sign-up resumes at AI Scan, after which authenticated reminder setup persists the nutrition plan and completes onboarding.
- A successful subscription purchase now continues through Benefits, Review, and Thank You before entering Today. Review submission remains optional; low ratings may include private authenticated feedback, while eligible positive ratings defer to the operating system's native store-review prompt.
